## 读法与效力

- 规则等级：【必须】= 规则，违反需用户明确豁免；【应该】= 准则，允许个别 derogate 但须说明理由并留痕。
- 规则末尾括号为来源追溯：`（源 H-X-Y）` = 行业编程规范章节-条号；`（先例 …）` = 跨项目历史事件沉淀；无标注为通用新增。
- 冲突时优先级：用户直接指令 > 项目指令文件（CLAUDE.md / AGENTS.md 等）> 项目版规范 > 本通用版 > 行业参照来源。
- 项目版可对本版**加密、特化**，不得无声**放宽**；放宽【必须】条目须用户批准并显式标注。
- 进入任何项目的第一动作：读项目指令文件与既有规范/文档，先贴合项目现状，再套用本版默认（0-8）。本版一切"默认"均在项目现状缺位时才启用。

## 0 总则

0-1 【必须】质量优先级：正确性 > 稳定性/安全性 > 可测试性 > 规范/可读性 > 全局效率 > 局部效率 > 个人偏好；发生冲突按此序裁决。（源 H-9-2）

0-2 【必须】语言：交流与交付物跟随用户交流语言（本用户默认简体中文）；注释/提交信息/文档跟随项目约定，项目无约定时与交流语言一致。

0-3 【必须】外部副作用授权红线：凡影响硬件、生产环境、外部服务、第三方或仓库外共享状态的操作（烧录、部署、发布、发送、删除共享数据、向外上传内容），须项目约定或用户授权方可执行；安全性不确定时停下来问，不侥幸。

0-4 【必须】流程链：澄清 → 设计 spec → 计划 → 实现（TDD 优先）→ 评审 → 验证 → 文档/memory 更新；跳过任何一环须用户同意。

0-5 【必须】未被明确要求修改/优化代码时，只做阅读操作，不改文件。

0-6 【必须】改码后总结：每次改动向用户交代改了什么、为什么、影响面、验证方式。

0-7 【必须】memory 与文档同步：里程碑结束写入该项目的持久 memory；memory 与代码/git 不一致时先以代码核实再纠正 memory。

0-8 【必须】先读后动：先读项目指令文件、既有规范、README 与相关文档；项目现状（风格、工具链、目录、分支策略）优先于本版默认。

0-9 【应该】单变量/最小_diff：一次改动只推进一个目标，保持可验证、可归因、可回退。

0-10 【必须】回复中的代码块禁止添加行号前缀，保证用户可直接复制粘贴。

## 1 排版与组织

1-1 【必须】项目现状优先：项目有格式化工具/配置/既有风格时遵循现状；本章其余条目为现状缺位时的默认。

1-2 【必须】缩进 4 空格，禁用 TAB。（源 H-1-1、1-8）

1-3 【必须】一行一条语句；控制关键字（if/for/while/switch/case/default 等）各自占行；受控体无论多少语句都加块界定符（C 系 {}；其他语言遵循该语言惯例）。（源 H-1-6、1-7）

1-4 【必须】C 系语言大括号 { } 各独占一行、同一列、与引用语句左对齐。（源 H-1-10）

1-5 【必须】行宽默认 < 80 字符；长表达式在低优先级操作符处换行，操作符置于新行之首并缩进。（源 H-1-3、1-4、1-12）

1-6 【必须】空格默认：双目操作符前后加空格；单目操作符与成员/指针访问符不加；逗号/分号只在后加；关键字与括号间加空格；括号内侧不加。（源 H-1-11）

1-7 【应该】相对独立程序块之间、变量说明之后加空行。（源 H-1-2）

1-8 【必须】不改动自动生成/生成器管辖的代码区域（代码生成器、脚手架、USER CODE 块等）；确需修改时改生成器输入或经用户批准。

1-9 【应该】连续同类赋值、连续宏/常量定义做对齐排版（`=` 与值纵向同列，尾部注释随之整齐）。

## 2 注释

2-1 【必须】注释准确、易懂、简洁；错误注释比无注释更有害；改码同时改注释，无用注释及时删除。（源 H-2-1、2-5、2-6）

2-2 【必须】文件/模块头注释：职责、在调用链中的上下游位置、关键配置、修改日志；凡覆盖/再配置它模块资源者，逐项列出再配置清单。

2-3 【必须】函数头注释：目的、输入、输出、返回值、调用关系、副作用（共享状态与外部资源）；处于并发/实时上下文者另须注明：执行上下文（中断/线程/异步）、最坏代价、可重入约束。（源 H-2-4）

2-4 【必须】有物理含义/业务含义的变量与常量注释含义、单位、取值范围。（源 H-2-9）

2-5 【必须】共享/全局变量较详细注释：职责、范围、存取者、并发关系（谁写谁读、可见性手段）。（源 H-2-11）

2-6 【必须】注释置于代码上方或右方，不可放下方；放上方时与上面代码空行隔开；与所描述内容同样缩排。（源 H-2-8、2-12、2-13）

2-7 【必须】变量定义、分支与循环语句必须编写注释；fall-through 必须加明确注释。（源 H-2-14、2-15）

2-8 【应该】注释写"为什么"（意图、权衡、先例提交号），不翻译"是什么"。

2-9 【应该】长/多重嵌套块结束行加结束标记注释。（源 H-½2-4）

2-10 【应该】有效注释量 ≥ 20% 作为参考目标。（源 H-2-1）

## 3 命名

3-1 【必须】遵循项目命名现状；引入新类别时模块内统一并在文件头说明。

3-2 【必须】完整单词或公认缩写（temp/tmp、flag/flg、msg、inc、stat）；特殊约定/缩写在源文件开始处注释说明。（源 H-3-1、3-2）

3-3 【必须】禁止单字符变量名（循环变量 i/j/k 等惯例例外）。（源 H-3-4）

3-4 【必须】互斥变量/相反动作用标准反义词组命名（add/remove、start/stop、open/close、send/receive、create/destroy 等）。（源 H-⅓3-3）

3-5 【必须】同一项目内风格一致，不混用多种命名体系。（源 H-3-5）

3-6 【应该】模块对外接口加模块前缀防命名/链接冲突。（源 H-⅓3-2）

3-7 【应该】函数名用动宾词组；避免 process/handle 等无义动词作唯一命名。（源 H-½6-13、建议6-14）

3-8 【必须】硬件/行业缩写（DMA/ADC/GPIO 等）进入标识符时按三档分级：函数名/变量名中缩写小写（adc_start_dma、gpio_pin）；宏/常量全大写；类型小写+后缀。三档不得混档，函数名禁现全大写段。推荐主流嵌入式生态小写族；大写族仅保留在厂商 SDK 层。

3-9 【必须】用户层采纳小写族（缩写小写 + snake_case）；厂商 SDK 层风格不镜像、不混入。

## 4 可读性

4-1 【必须】用括号/显式结构明确操作顺序，不依赖默认优先级与隐式规则。（源 H-4-1）

4-2 【必须】禁止魔法数：有含义的常量用具名常量/枚举或就地注释。（源 H-4-2）

4-3 【应该】关系紧密的代码相邻；不用难懂的高技巧语句（高技巧 ≠ 高效率）。（源 H-½4-1、½4-2）

## 5 数据与结构

5-1 【必须】严禁未经初始化的变量作右值，尤其指针/引用。（源 H-5-6）

5-2 【必须】跨并发域（中断/线程/异步/进程）的共享状态：单写者优先，否则显式同步；按语言内存模型做可见性保证（volatile/atomic/锁），并注释"谁写谁读"。

5-3 【必须】跨边界（硬件/协议/进程/语言/存储）的数据用显式宽度类型与显式序列化约定，考虑字节序、对齐、版本兼容。（源 H-½5-2、½5-15）

5-4 【必须】缓冲区/容器在边界处显式约束尺寸与对齐，防越界；关键尺寸常量附警示注释。

5-5 【必须】共享变量最小化；公共状态仅一个模块可写、其余只读。（源 H-5-1、½5-1）

5-6 【必须】隐式转换陷阱必须显式防御或注释：符号扩展、无符号下溢、收窄、溢出。（源 H-½5-10、½5-11、½9-6、½9-7）

5-7 【应该】结构功能单一，不设计面面俱到的灵活结构；布局考虑对齐与向前兼容。（源 H-½5-3~½5-8）

## 6 函数与并发

6-1 【必须】所调用函数的错误返回码/异常仔细、全面处理，不吞错。（源 H-6-1）

6-2 【必须】一个函数仅完成一件功能；规模 ≤ 200 行（不含注释和空行）；不设计多用途面面俱到的函数。（源 H-½6-2、½6-3、½6-5）

6-3 【必须】处于并发/实时/热上下文（中断、持锁、异步回调、热路径）的代码：不阻塞、不做未经批准的重量级操作、不打无开关的日志；代价须估算并注释，项目有预算模型者纳入预算。

6-4 【必须】并发/实时架构属红线：动优先级、锁序、调度、阻塞方式的改动，先更新设计说明，经设计级评审与用户批准。

6-5 【必须】可重入：跨上下文共用的函数不依赖未受保护的静态/全局状态；必须共享时按 5-2 保护并注释。（源 H-6-3、6-4）

6-6 【必须】参数合法性检查责任明确且统一：对外输入由接口自身检查，内部紧耦合调用由调用者负责；同一模块内分工一致。（源 H-6-5 改编）

6-7 【应该】不将参数作工作变量；先局部临时、结束前回赋。（源 H-½6-1）

6-8 【应该】函数行为可预测：相同输入相同输出；隐藏状态（static/缓存/记忆化）须有意为之并注释。（源 H-½6-6、½11-13）

6-9 【应该】不依赖其它函数内部实现；减少递归；扇出合理（3-5，<7），公共/底层函数追求高扇入。（源 H-½6-7、½6-23、½6-24）

6-10 【应该】非调度函数用数据参数、不用控制参数；避免布尔参数。（源 H-½6-9、½6-28）

## 7 常量、宏、配置

7-1 【必须】优先使用语言原生常量/内联函数；C 系表达式宏必须完备括号（参数与整体皆括）。（源 H-12-1）

7-2 【必须】多条语句宏用 do{...}while(0) 或大括号包裹；宏参数不得带副作用。（源 H-12-2、12-3）

7-3 【必须】功能开关集中管理并注释：含义、当前值、恢复方法；骨架保留、整体可恢复。

7-4 【必须】诊断/调试代码开关化、可整体移除，release 去掉或静默；不同时维护 DEBUG/正式两套源文件（用开关或分支策略二选一落地）。（源 H-7-14、7-15）

7-5 【应该】编译期/加载期可算的不得运行期重复算。（源 H-½8-11）

## 8 可测性、测试

8-1 【必须】TDD 优先：新逻辑模块先写测试、测试先行；优先宿主/仿真等不触碰真实环境的测试手段。

8-2 【必须】测试覆盖边界：阈值边界、量程/容量边界、时间边界（回绕/超时）、空/满/错误输入。（源 H-7-4、½11-5）

8-3 【必须】断言只用于"正常运行不应发生、但调测时可能发生"的非法情况；预期会发生的错误写防错程序处理，不得以断言代替。（源 H-7-6、7-7）

8-4 【必须】断言与诊断打印开关化、可摘除；诊断的加入/摘除不改变功能行为。（源 H-7-12、7-13）

8-5 【必须】诊断输出格式统一、带模块名与定位信息；不随意新增诊断通道；临时打印及时删除或开关化。（源 H-7-1、7-2）

8-6 【必须】涉及真实环境/硬件/生产/用户的验证用户驱动：我给出验证判据与步骤，用户执行或授权后执行。（呼应 0-3）

8-7 【应该】写码前先设计测试手段：测项、判据、可复用诊断资产先列清。（源 H-½7-1）

8-8 【应该】关键算法/关键数值用独立方法交叉确认。（源 H-½9-5）

8-9 【应该】调测开关分级别和类型（模块级、功能级、性能级）。（源 H-½7-2）

## 9 效率

9-1 【必须】全局效率优先：先识别项目的瓶颈资源（实时节拍、内存、带宽、延迟、成本），局部优化服务全局瓶颈。（源 H-8-3）

9-2 【必须】预算模型：瓶颈约束存在时，热路径改动给出最坏代价估算并在落地前后实测；设告警与必须处理的阈值。

9-3 【必须】构建/优化/依赖配置是设计的一部分，须版本化；构建前核对配置与仓库版本化状态一致（防 IDE 回写、本地未提交覆盖等工具链漂移）。

9-4 【应该】循环体内工作量最小化；循环不变量外提；最忙循环放最内层；减少嵌套层次。（源 H-8-5、½8-8~½8-10）

9-5 【应该】热路径以廉价运算代替昂贵运算（如乘法代除法、整数代浮点，视平台而定）。（源 H-½8-11）

9-6 【应该】不一味追求紧凑代码（紧凑 ≠ 高效机器码）；不拼命优化冷路径；汇编/内联/底层优化仅限极热路径并附实测数据。（源 H-½8-5、½8-6、½8-12）

9-7 【应该】空间效率靠数据结构划分与算法优化提高，不靠压缩代码量。（源 H-8-4、½8-7）

## 10 质量保证

10-1 【必须】只引用属于自己的空间；防越界；防引用已释放资源；打开的资源（内存/句柄/连接/外设）在所有退出路径（含提前返回/异常）关闭释放。（源 H-9-3~9-7）

10-2 【必须】启动时初始化有关变量与环境；加载/持久化数据做一致性检查，违例回退安全默认。（源 H-9-9、9-10）

10-3 【必须】不随意更改其它模块/系统的设置和接口：跨边界改动须设计说明 + 用户批准，并以清单注释落地。（源 H-9-11~9-13）

10-4 【必须】防差 1 错误：边界比较与循环写毕重看首末两轮。（源 H-9-14）

10-5 【必须】写完代码通扫一遍本语言易混淆符号（= / ==、& / &&、| / ||、< / <= 等）。（源 H-9-15）

10-6 【必须】分支覆盖 else/default，缺省须说明理由。（源 H-9-16）

10-7 【必须】不滥用 goto 及等价的非结构化跳转。（源 H-9-18）

10-8 【必须】项目已记录的边界与约束当约束对待：相关改动须重新评估并注释。

10-9 【应该】第三方代码/库/工具不过分相信其正确性：接口层了解后再用，遇异常对照官方文档/源码核实。（源 H-½9-12）

10-10 【应该】关键假设用编译期/静态检查或断言固定（类型尺寸、对齐、不变量）。（源 H-7-11）

## 11 编辑、构建、审查

11-1 【必须】打开编译器/解释器所有警告开关；新代码零警告；确信误报用局部抑制并注释理由，禁止全局关警告。（源 H-10-1、½10-5）

11-2 【必须】构建配置统一且版本化；构建前核对：源文件/依赖清单、优化等级、工具链本地漂移（IDE 回写旧模型、环境差异）。（源 H-10-2）

11-3 【必须】评审门：每任务自审 + 独立评审；合并/发布前最终评审；评审发现逐条闭环，延后项留痕。（源 H-10-3）

11-4 【必须】git 为唯一备份：及时提交（进度可暂存提交并注明）；提交信息含"什么 + 为什么"，跟随项目语言约定；清理类提交保持纯删除式。（源 H-½10-1、11-5）

11-5 【应该】块拷贝粘贴后，把粘贴块内每个变量、标识符重看一遍。（源 H-½10-3）

11-6 【应该】文档组织遵循项目现状；新增文档入项目既定目录。（源 H-½10-4）

11-7 【必须】活动 IDE/构建工具实例回写旧模型时：先断循环（关闭编辑器或经其界面操作）再动构建配置；在对方基线上只同步失效路径，不回滚对方结构性写回。

11-8 【必须】零逻辑变化重构必附静态自检（括号平衡、残留 grep、TAB/行尾空白）；改名用精确令牌替换，宏/类型防误伤。

11-9 【必须】重构逐项授权、逐项总结、逐项审核；提交粒度按重构主题拆分。

11-10 【必须】git 提交（含粒度拆分与提交信息）须经用户审核批准后方可执行；未经授权不提交。

11-11 【必须】提交信息站在仓库主人（用户）视角陈述改了什么、为什么；不用第三方口吻；不得出现第三方公司名及其专有文档名，来源一律泛称（如"行业编程规范"）。

## 12 测试、维护

12-1 【必须】根因不试错：证据 → 假设 → 判别实验 → 根因闭环；禁止"试到行为止"。（源 H-½11-7、½11-9）

12-2 【必须】自动消失的错误必须分析到消失机理，不得"消失即解决"。（源 H-½11-8）

12-3 【必须】修复留痕：commit message + 项目文档 + 持久 memory，保证可追溯。（源 H-11-6、½11-6）

12-4 【必须】清理/优化后的代码重新审查与测试；工具链/依赖/配置升级视为需验证的变更。（源 H-11-3、11-4）

12-5 【应该】使很少发生的事件经常发生（force 开关、故障注入、压测）；明确模块处理哪些事件并使它们发生。（源 H-½11-10、½11-11）

12-6 【应该】保留测试信息（日志、波形、输出、快照）于可检索位置。（源 H-½11-6）

12-7 【应该】去除代码行为随机性，使结果可预测、错误可再现。（源 H-½11-13）

## 13 架构与模块化

13-1 【必须】模块即类：模块状态私有（static 或封装），对外仅接口函数；写方单点收敛。

13-2 【必须】跨模块可变全局量禁用；例外仅"单写者 + 只读快照/只读指针"两形态，并注释谁写谁读。

13-3 【必须】分层方向约束：下层不得依赖上层类型；层间只经接口函数交互。

13-4 【必须】include-what-you-use：头文件不替 .c 背实现依赖；god header 禁用。

13-5 【应该】解耦机制优先级：函数指针插件槽（多态）、回调反转、表驱动；OO 化以"多实例/多态/宿主可测"三红利为判据，单实例实体不 handle 化，防过度抽象。

## 14 目录结构

14-1 【必须】用户代码与生成代码分离：生成目录只留生成物，用户代码按层分目录。

14-2 【必须】目录命名大小写统一；动目录必同步构建配置（源清单 + include 路径）与项目说明文档。

14-3 【必须】文件名 = 模块名 = 符号前缀三重对齐。
