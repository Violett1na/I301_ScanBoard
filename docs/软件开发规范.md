## 读法与效力

- 规则等级：【必须】= 规则，违反需用户明确豁免；【应该】= 准则，允许个别 derogate 但须在注释或提交信息中说明理由。
- 规则末尾括号为来源追溯：`（源 H-X-Y）` = 行业编程规范章节-条号；`（AGENTS）` = 继承仓库 AGENTS.md；`（先例 …）` = 本项目历史事件沉淀；`（项目）` = 本项目特性新增。
- 冲突时优先级：用户直接指令 > 项目指令文件（AGENTS.md 等）> 本规范（项目版）> 通用版 > 行业参照来源。项目版可对通用版加密、特化，不得无声放宽；放宽【必须】条目须用户批准并显式标注。
- 附录 A 为动态约束清单，须与 release notes（及其后续版本）同步更新。

## 0 总则

0-1 【必须】质量优先级：正确性 > 稳定性/安全性 > 可测试性 > 规范/可读性 > 全局效率 > 局部效率 > 个人偏好；发生冲突按此序裁决。（源 H-9-2）

0-2 【必须】全程中文：回复、思考、注释、提交信息、文档一律简体中文。（AGENTS）

0-3 【必须】硬件安全优先于任何软件便利：JP3 必须断开；目标固件的编译/烧录须用户授权（宿主单测 WSL gcc 除外）；电气安全性不确定时停下来问，不侥幸。（项目）

0-4 【必须】流程链：澄清 → 设计 spec → 计划 → 实现（TDD 优先）→ 逐任务评审 → 最终评审 → 用户上板验证 → 文档/memory 更新；跳过任何一环须用户同意。（项目）

0-5 【必须】改码后总结：每次改动向用户交代改了什么、为什么、影响面、验证方式。（AGENTS）

0-6 【必须】未被明确要求修改/优化代码时，只做阅读操作，不改文件。（AGENTS）

0-7 【必须】memory 与文档同步：里程碑结束更新持久 memory 与仓库文档；memory 与 git/代码不一致时先以代码核实再纠正 memory。（项目）

0-8 【应该】单变量原则：一次改动只推进一条功能链，保持上板对照的可归因性。（先例：OCD_ENABLE 摘除 21f88c8）

0-9 【必须】回复中的代码块禁止添加行号前缀，保证用户可直接复制粘贴。（AGENTS）

## 1 排版

1-1 【必须】缩进 4 空格，禁用 TAB。（源 H-1-1、1-8）

1-2 【必须】一行一条语句；if/for/do/while/case/switch/default 各自占行；if/for/do/while 执行部分无论多少语句都加 {}。（源 H-1-6、1-7）

1-3 【必须】大括号 { } 各独占一行、同一列、与引用语句左对齐。（源 H-1-10）

1-4 【必须】行宽 < 80 字符；长表达式在低优先级操作符处换行，操作符置于新行之首并缩进。（源 H-1-3、1-4、1-12）

1-5 【必须】空格：双目操作符（=、+=、+、&&、&、<<、^、比较符等）前后加空格；单目操作符（!、~、++、--、取址 &）与 ->、. 不加；逗号/分号只在后加；if/for/while/switch 与括号间加空格；括号内侧不加；非对齐排版不连续留两个以上空格。（源 H-1-11）

1-6 【必须】对齐排版：连续同类赋值语句 `=` 纵向同列；连续宏定义宏名、宏值纵向同列，尾部注释随之整齐。（AGENTS）

1-7 【应该】相对独立程序块之间、变量说明之后加空行。（源 H-1-2）

1-8 【必须】不改动 CubeMX 自动生成代码区域（只写 USER CODE BEGIN/END 之间）。（AGENTS）

## 2 注释

2-1 【必须】有效注释量 ≥ 20%；注释准确、易懂、简洁；错误注释比无注释更有害；改码同时改注释，无用注释同提交删除。（源 H-2-1、2-5、2-6）

2-2 【必须】文件头注释：功能、在调用链中的上下游位置、关键配置宏、修改日志；凡"再配置/覆盖"它模块外设的文件，逐项列出再配置清单。（先例：ocd_sig.c 文件头再配置清单①~⑤）（源 H-2-2、2-3）

2-3 【必须】函数头注释：目的、输入、输出、返回值、调用关系、副作用（触碰的全局变量与硬件寄存器）；ISR/DMA 回调另须注明：中断优先级、最坏周期消耗、可重入约束。（源 H-2-4）

2-4 【必须】有物理含义的变量/常量注释含义、单位、取值范围（radc = 电位器码值、comp = 偏置补偿、0..4095 = DAC 码等）。（源 H-2-9、AGENTS）

2-5 【必须】全局变量较详细注释：功能、范围、存取函数、并发关系（ISR 写/主循环读、是否 volatile）。（源 H-2-11）

2-6 【必须】注释置于代码上方或右方，不可放下方；放上方时与上面代码空行隔开；与所描述内容同样缩排。（源 H-2-8、2-12、2-13）

2-7 【必须】变量定义、分支与循环语句必须编写注释；case fall-through 必须加明确注释。（源 H-2-14、2-15）

2-8 【应该】注释写"为什么"（意图、权衡、先例提交号），不翻译"是什么"；关键警示注释引用先例根因提交。（先例：task.h AD_DA_BLOCK"勿再改小"警示）（源 H-½2-3）

2-9 【应该】长/多重嵌套程序块结束行右方加结束标记注释。（源 H-½2-4）

2-10 【应该】注释格式尽量统一；中文优先。（源 H-½2-5、½2-6）

## 3 命名

3-1 【必须】函数名 `模块_功能` 小写 snake_case；宏/常量全大写+下划线；结构体类型小写+`_t`；枚举类型小写+`_e`；头文件保护 `__文件名_H__`。（AGENTS）

3-2 【必须】完整单词或公认缩写（temp/tmp、flag/flg、msg、inc、stat）；特殊约定/缩写在源文件开始处注释说明。（源 H-3-1、3-2）

3-3 【必须】禁止单字符变量名（i/j/k 作局部循环变量例外）。（源 H-3-4）

3-4 【必须】互斥变量/相反动作用标准反义词组命名（trip/release、start/stop、open/close、send/receive、add/remove 等）。（源 H-⅓3-3）

3-5 【应该】模块对外接口加模块前缀防链接冲突（ocd_sig_*、ocd_*、ad_da_*）。（源 H-⅓3-2）

3-6 【应该】函数名用动宾词组；避免 process/handle 等无义动词作唯一命名。（源 H-½6-13、建议6-14）

3-7 【必须】缩写大小写三档分级：函数名/变量名中缩写一律小写（ad5290_set_code、adc_value、dma 句柄）；宏/常量全大写（AD_DA_BLOCK、DMA_REQUEST_DAC1_CHANNEL1）；类型小写+后缀（adc_value_t、log_level_e）。三档不得混档——函数名禁现全大写段（AD_DA_Init 式像宏，违例）。参照主流嵌入式生态小写族（缩写小写 + snake 式）；大写族仅存在于厂商 SDK 层（调用照原样），用户层不采用。

3-8 【必须】命名族选定小写族：用户层函数/变量一律"缩写小写 + snake_case"；厂商层风格不镜像、不混入。

## 4 可读性

4-1 【必须】用括号明确操作顺序，不依赖默认优先级。（源 H-4-1）

4-2 【必须】禁止魔法数：有物理意义的常量用具义宏/枚举或就地注释（4095 = 满量程码、8 = 连续撞轨样本阈值、1s = 防抖释放时长等）。（源 H-4-2）

4-3 【应该】关系紧密的代码相邻；不用难懂的高技巧语句（高技巧 ≠ 高效率）。（源 H-½4-1、½4-2）

## 5 变量、类型、结构

5-1 【必须】严禁未经初始化的变量作右值，尤其指针。（源 H-5-6）

5-2 【必须】ISR 与主循环共享变量必须 volatile，并注释"谁写谁读"。（项目）

5-3 【必须】跨硬件/协议边界的数据用显式宽度类型（uint8/16/32_t），寄存器/协议字段禁裸 int。（源 H-½5-2）

5-4 【必须】DMA 缓冲区用定长数组+尺寸宏，保证对齐与不越界；块长宏附警示注释并引用先例根因。（先例：AD_DA_BLOCK=32，b65daf6）（项目）

5-5 【必须】全局变量最小化；公共变量仅一个模块可写、其余只读。（源 H-5-1、½5-1）

5-6 【必须】隐式类型转换陷阱必须显式防御或注释：符号扩展（char -1 → unsigned short 0xFFFF）、无符号下溢（size-- >= 0 死循环）、收窄。（源 H-½5-10、½5-11、½9-6、½9-7）

5-7 【应该】局部变量不与全局同名；结构功能单一，不设计面面俱到的灵活结构；结构布局考虑对齐、位域相邻；跨 CPU 结构考虑字节序与对齐。（源 H-5-5、½5-3~½5-8、½5-15）

## 6 函数、中断上下文

6-1 【必须】所调用函数的错误返回码仔细、全面处理（HAL 状态、协议解析、flash 读写）。（源 H-6-1）

6-2 【必须】一个函数仅完成一件功能；规模 ≤ 200 行（不含注释和空行）；不设计多用途面面俱到的函数。（源 H-½6-2、½6-3、½6-5）

6-3 【必须】ISR/DMA 回调三禁：不阻塞（HAL_Delay、等待循环）、不浮点/除法（除非实测批准）、不打调试打印；最坏周期消耗须估算并注释，且纳入节拍预算。默认遵循 AGENTS：中断回调尽量短、只做数据搬运和标志位；1MHz 实时管线为已批准例外，按预算模型管理（见 6-4）。（项目、AGENTS）

6-4 【必须】中断优先级架构属红线：现管线 ISR 优先级 0、SysTick 优先级 15，已知边界"预算被穿即整机冻结且自锁"（release notes）；凡动优先级、预算、块长的改动，先更新预算模型，经设计文档级评审与用户批准。（项目）

6-5 【必须】可重入：ISR 与主循环共调的函数不用 static 局部变量；共享状态 volatile 单写者或关中断保护，并注释。（源 H-6-3、6-4）

6-6 【必须】参数合法性检查责任明确且统一：对外输入（协议包、上位机命令）由接口函数自身检查；内部紧耦合调用由调用者负责；同一模块内分工一致。（源 H-6-5 改编）

6-7 【应该】不将参数作工作变量；先局部临时变量、结束前回赋。（源 H-½6-1）

6-8 【应该】函数行为可预测：相同输入相同输出；static 局部（"内部寄存器"）须有意为之并注释，写明复位路径。（源 H-½6-6、½11-13）

6-9 【应该】不依赖其它函数内部实现；减少递归；扇出合理 3-5（<7），公共/底层函数追求高扇入。（源 H-½6-7、½6-23、½6-24）

6-10 【应该】非调度函数用数据参数、不用控制参数；避免 BOOL 参数。（源 H-½6-9、½6-28）

## 7 宏、条件编译

7-1 【必须】表达式宏完备括号（参数与整体皆括）。（源 H-12-1）

7-2 【必须】多条语句宏用 do{...}while(0) 或大括号包裹；宏参数不得带副作用（a++ 禁作实参）。（源 H-12-2、12-3）

7-3 【必须】功能开关用"宏骨架 + #if"模式集中于模块头文件，注释开关含义、当前值、恢复方法。（先例：OCD_SIG_ENABLE=1、OCD_ENABLE=0）（项目）

7-4 【必须】诊断/调试代码只能经条件编译或 Debug 分支进入代码库，且整体可移除；不同时维护 DEBUG/正式两套源文件——本项目以双分支策略落地：Debug 保留诊断、master release 删除式清理。（源 H-7-14、7-15）

7-5 【应该】编译期常量优先于运行期计算；倒数等可编译期算出的不得运行期算。（源 H-½8-11）

## 8 可测性、测试

8-1 【必须】TDD：新逻辑模块（尤其状态机）先写宿主单测（WSL gcc）、测试先行再嵌入固件；测试与被测同提交序列推进。（源 H-7-3、½7-1、½11-12；先例：ocd_sig Task 1）

8-2 【必须】单测覆盖边界：阈值边界（连续撞轨判据）、量程边界（0/4095）、时间边界（uint32 毫秒回绕）。（源 H-7-4、½11-5）

8-3 【必须】断言只用于"正常运行不应发生、但调测时可能发生"的非法情况；预期会发生的错误写防错程序处理，不得以断言代替。（源 H-7-6、7-7）

8-4 【必须】断言与诊断打印须开关化、可摘除，release 去掉或静默；诊断的加入/摘除不改变功能行为。（源 H-7-12、7-13）

8-5 【必须】诊断输出格式统一、带模块名与定位信息；上板诊断复用既有通道（串口时间戳、VOFA），不随意新开通道；临时打印及时删除或改开关化。（源 H-7-1、7-2、AGENTS）

8-6 【必须】上板验证用户驱动：我给出验证判据，用户构建、烧录、测量。（先例：OCD_ENABLE 上板三判据）（项目，呼应 0-3）

8-7 【应该】写码前先设计测试手段：宿主测项、上板判据、可复用的诊断资产（Debug 分支）先列清。（源 H-½7-1）

8-8 【应该】关键算法用独立方法交叉确认。（先例：全链周期以反汇编实测回证）（源 H-½9-5）

8-9 【应该】调测开关分级别和类型（模块级、功能级、性能级）。（源 H-½7-2）

## 9 程序效率

9-1 【必须】全局效率优先：ISR 管线是全局瓶颈；主循环与辅助代码不与其争优先级、争带宽；局部效率服务全局。（源 H-8-3）

9-2 【必须】预算模型：凡进入 ISR 链的代码给出最坏周期估算并在落地前后实测；占用 >70% 预算告警、>90% 必须处理（砍链路、块长、优先级设计）。（先例：b65daf6）（项目）

9-3 【必须】优化等级是设计的一部分：本项目 ≥ level-2（level-0 必冻结，历史结论）；构建前检查 eide.yml 优化等级与源文件列表。（先例：EIDE 实例回写旧模型环境隐患）（项目）

9-4 【应该】循环体内工作量最小化；循环不变判断外提；最忙循环放最内层；减少嵌套层次。（源 H-8-5、½8-8~½8-10）

9-5 【应该】热路径以乘法代除法，尤其浮点除法；倒数编译期计算。（源 H-½8-11）

9-6 【应该】不一味追求紧凑代码（紧凑 ≠ 高效机器码）；不拼命优化冷路径；汇编嵌入仅限极热函数并附实测数据。（源 H-½8-5、½8-6、½8-12）

9-7 【应该】空间效率靠数据结构划分与算法优化提高，不靠压缩代码量。（源 H-8-4、½8-7）

## 10 质量保证

10-1 【必须】只引用属于自己的存贮空间；防越界（数组/指针/DMA 缓冲区）；防引用已释放内存；函数内打开的资源（内存/句柄/外设）在退出前含全部提前返回路径关闭释放。（源 H-9-3~9-7）

10-2 【必须】系统运行之初初始化有关变量及运行环境；加载数据做一致性检查（flash 参数加载应验范围、违例回退默认）。（源 H-9-9、9-10）

10-3 【必须】不随意更改其它模块的设置和接口：跨模块宏/寄存器/协议改动须设计文档说明 + 用户批准，并以再配置清单注释落地。（先例：ocd_sig 覆盖 DAC/OPAMP5 配置）（源 H-9-11~9-13）

10-4 【必须】防差 1 错误：<=/>= 与循环边界写毕重看首末两轮。（源 H-9-14）

10-5 【必须】写完代码通扫一遍易混淆操作符：=/==、&/&&、|/||、</<=、>/>=。（源 H-9-15）

10-6 【必须】if 尽量带 else，无 else 说明理由；switch 必须有 default。（源 H-9-16）

10-7 【必须】不滥用 goto。（源 H-9-18）

10-8 【必须】已知边界当约束对待（JP3 断开、上电假跳闸 ~1s、无看门狗、优先级架构边界）：相关改动须重新评估这些边界并注释。（项目）

10-9 【应该】第三方代码（HAL 等）接口层了解后再使用，不过分相信其正确性；遇异常对照源码/datasheet 核实。（源 H-½9-12）

10-10 【应该】关键假设用编译期检查或断言（sizeof/对齐、块长偶性等）。（源 H-7-11）

10-11 【应该】初始化阶段致命错误走统一 Error_Handler；运行时故障（过流等）走设计的信令链路，不擅自死循环化。（AGENTS 改编）

## 11 编辑、编译、审查

11-1 【必须】打开编译器所有警告开关；新代码零警告；确信误报用局部 pragma 处理并注释理由，禁止全局关警告。（源 H-10-1、½10-5）

11-2 【必须】编译开关统一且版本化（eide.yml 在库）；构建前三查：源文件列表、优化等级、用户 EIDE 实例是否持旧模型；必要时提示用户重载工程。（源 H-10-2；先例：环境隐患）（项目）

11-3 【必须】评审门：每任务自审 + 独立评审；合并/烧录前最终评审；评审发现逐条闭环，延后项记入 docs/memory。（源 H-10-3）

11-4 【必须】git 为唯一备份：及时提交（进度可暂存提交并注明）；提交信息中文、含"什么+为什么+先例编号"；release 清理提交保持纯删除式。（源 H-½10-1、11-5）

11-5 【应该】块拷贝粘贴后，把粘贴块内每个变量、标识符重看一遍。（源 H-½10-3）

11-6 【应该】新增文档入 docs/，设计/计划类文档日期前缀；目录结构遵循仓库现状。（源 H-½10-4）

11-7 【必须】活动 IDE 实例回写旧模型时：先断循环（关闭编辑器或经其界面操作）再动构建配置；在对方基线上只同步失效路径，不回滚对方结构性写回。（先例：EIDE 实例回写 eide.yml）

11-8 【必须】零逻辑变化重构必附静态自检（括号平衡、残留 grep、TAB/行尾空白）；改名用精确令牌替换，宏/类型防误伤。

11-9 【必须】重构逐项授权、逐项总结、逐项审核；提交粒度按重构主题拆分。

11-10 【必须】git 提交（含粒度拆分与提交信息）须经用户审核批准后方可执行；未经授权不提交。（2026-08-31 用户指令入规）

11-11 【必须】提交信息站在仓库主人（用户）视角陈述改了什么、为什么（参照"进度暂存(用户手改)"式样），不用第三方口吻（如"用户审核通过"）；不得出现第三方公司名及其专有文档名，来源一律泛称（如"行业编程规范"）。（2026-08-31 用户指令入规）

## 12 测试、维护

12-1 【必须】根因不试错：证据 → 假设 → 判别实验 → 根因闭环；禁止"试到行为止"。（源 H-½11-7、½11-9；先例：整机冻结根因排查）

12-2 【必须】自动消失的错误必须分析到消失机理，不得"消失即解决"。（先例：冻结自锁链解释"昨天好今天冻"）（源 H-½11-8）

12-3 【必须】修复留痕三处：commit message + 仓库 docs + 持久 memory，保证可追溯。（源 H-11-6、½11-6）

12-4 【必须】清理/优化后的代码重新审查与测试；编译器/HAL/优化等级升级视为需验证的变更。（源 H-11-3、11-4）

12-5 【应该】使很少发生的事件经常发生（force 开关、故障注入）；明确模块处理哪些事件并使它们发生。（源 H-½11-10、½11-11）

12-6 【应该】保留测试信息（波形、日志、反汇编）于 docs/memory，附可检索路径。（源 H-½11-6）

12-7 【应该】去除代码行为随机性，使结果可预测、错误可再现。（源 H-½11-13）

## 13 架构、分层与模块化

13-1 【必须】模块即类：模块状态私有（static 或封装），对外仅接口函数；写方单点收敛。（先例：param.c 三量私有化）

13-2 【必须】跨模块可变全局量禁用；例外仅"单写者 + 只读快照/只读指针"两形态，并注释谁写谁读。（先例：adc_value、param_comp）

13-3 【必须】分层方向约束：下层不得依赖上层类型；层间只经接口函数交互。（先例：bsp_flash 不得含应用层头）

13-4 【必须】include-what-you-use：头文件不替 .c 背实现依赖；god header 禁用。（先例：task.h 曾替 task.c 背协议链）

13-5 【应该】解耦机制优先级：函数指针插件槽（多态）、回调反转、表驱动；OO 化以"多实例/多态/宿主可测"三红利为判据，单实例硬件实体不 handle 化，防过度抽象。（先例：算法槽、协议回调注册、ad5290 引脚表、ocd_sig 双轴实例）

## 14 目录结构

14-1 【必须】用户代码与生成代码分离：生成目录只留生成物（Core），用户代码按层分目录（App/Bsp/Proto/USB）。

14-2 【必须】目录命名大小写统一（Inc/Src）；动目录必同步构建配置（源清单 + include 路径）与 README。

14-3 【必须】文件名 = 模块名 = 符号前缀三重对齐。（先例：task → ad_da）
